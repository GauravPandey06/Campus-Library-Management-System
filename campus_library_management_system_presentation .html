Context & Motivation Slide 02 / 08

Problem Statement & Solution Overview

Eliminating manual ledger inefficiencies through automated, concurrent software design.

✕

Legacy Physical System Challenges

  • • Manual Clerical Overhead: Paper record entries result in human transcription errors and duplicate registrations.
  • • No Real-Time Stock Visibility: Students cannot verify availability without walking to the issue desk.
  • • Concurrency Race Conditions: Concurrent checkout requests cause negative inventory when the last copy is claimed.
  • • Unreliable Audit Trails: Return dates and transaction histories are easily lost or misplaced.
✓

Automated Software Solution

  • • Role-Specific Desktop UI: Unified Java Swing interface offering tailored Librarian and Member views.
  • • Persistent SQLite Database: Atomic JDBC operations ensure real-time inventory updates and persistence.
  • • Thread-Safe Concurrency: Mutual exclusion lock (ReentrantLock) serializes critical checkout transactions.
  • • Robust Exception Pipeline: Custom checked exceptions guard business rules with instant visual alerts.
Key Objective: Deliver a self-contained, high-performance circulation system meeting all 30 rubric points. Zero External Server Dependencies

Relational ER Schema (library.db)

TABLE: books Inventory Entity
PK id : INTEGER AUTOINCREMENT
• title : TEXT NOT NULL
• author : TEXT NOT NULL
• isbn : TEXT UNIQUE
• genre : TEXT
• copies : INTEGER (Available Stock)
TABLE: transactions Audit History
PK id : INTEGER AUTOINCREMENT
FK book_id : INTEGER (References books.id)
• user_id : INTEGER (Active Member)
• borrow_date : TEXT (Timestamp)
• return_date : TEXT (Timestamp / 'N/A')
• status : TEXT ('BORROWED' / 'RETURNED')
Foreign Key relation guarantees complete traceability between circulation history and physical books. Database Driver: org.xerial.sqlite-jdbc

Concurrency & Data Security Slide 05 / 08

Concurrency, Thread Safety & JDBC Operations

Eliminating race conditions via ReentrantLock while preventing SQL injection attacks.

ReentrantLock Synchronization Mutual Exclusion 
// Prevent Double Checkout Glitch
private static final ReentrantLock lock = 
    new ReentrantLock();

lock.lock(); // Acquire critical section
try {
    if (copies > 0) {
        updateCopies(copies - 1);
        recordTransaction();
    } else {
        throw new BookNotAvailableException();
    }
} finally {
    lock.unlock(); // Always released
}

Guarantees thread safety when multiple worker threads process checkout requests simultaneously.

PreparedStatement Security Anti-SQL Injection 
// Parameterized & Atomic Transaction
conn.setAutoCommit(false);

String sql = "INSERT INTO transactions " + 
             "(book_id, user_id, borrow_date) " +
             "VALUES (?, ?, ?)";

PreparedStatement ps = conn.prepareStatement(sql);
ps.setInt(1, bookId);
ps.setInt(2, userId);
ps.setString(3, currentTimestamp);
ps.executeUpdate();

conn.commit(); // Explicit commit on success

Typed bindings neutralize malicious injection inputs; manual commit rollbacks maintain ACID consistency.

Non-Blocking GUI: Work performed in worker threads with results pushed to Swing EDT via SwingUtilities.invokeLater().
Database Safety: All JDBC connections instantiated inside try-with-resources preventing resource leaks.
